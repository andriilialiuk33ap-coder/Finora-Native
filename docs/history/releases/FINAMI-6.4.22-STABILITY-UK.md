# Finami 6.4.22 / Build 70 — фінансова цілісність I

База: Build 69. Мета — обмежене, перевірюване вдосконалення наявних функцій. Не змінено формат БД, Aurora Balance, Fusion Crystal, OCR, маршрутизацію вкладок чи правила фінансової класифікації.

## Зміни
- `FinamiPaymentCore`: діагностика повтору ID запису, повторного прив'язування дебету, відсутньої операції, невідповідності її напряму, рахунку, нативної суми та валюти; обмеження записаної суми. Позначка оплати без списання і історія видаленого/архівного договору допускаються. Виявлені в старій БД дефекти не переписуються й не блокують незалежні дії. Порівняння кількості проблем запобігає їх збільшенню. Це не механізм автоматичного ремонту.
- `Store.prepareChange` (звичайний і асинхронний пакетний запис), `replaceOperationsForImport`: новий захист перед комітом. Існуючі перевірки пов'язаних операцій, повернень і групових переказів збережено. Повне відновлення з резервної копії не змінено — окремий етап.
- `FinamiAuditCore`: нові проблеми видно в наявному розділі якості фінансових даних, без автоматичної зміни сум і без виведення ID в заголовках.
- `IzanamiFeatures`: блок банківських комісій використовує `expenseGroup`/`expenseValue` і спільний `Store.totals`, включно з підтвердженими вбудованими комісіями й поверненнями.
- `FinamiExportReport`: збережено валові категорії, додано чисті категорії і чистий внесок кожної операції. Вбудована комісія потрапляє до витрат лише як її сума (окрема колонка); загальна сума руху залишається в старій колонці. Внутрішнє фільтрування за рахунком узгоджує підсумки та рядки. Маскування нових колонок підкоряється наявному параметру includeAmounts.

## Критерії і рівень покриття
| ID | Сценарій | Доказ |
|---|---|---|
| FC-01 | Два UAH-рахунки, покупка, дохід, переказ, повернення, компенсація, комісія, погашення | `check-build63-receipts.sh`: фіксовані еталонні баланси та чисті суми, звіт, дашборд, нативна активність, експорт |
| FC-02 | Редагування суми/категорії, JSON roundtrip, видалення комісії | той самий тест; тестуються моделі і обчислення, не справжня iOS-персистенція |
| FC-03 | Нові та старі дефекти зв'язків оплат, USD, позначка без списання | той самий тест: нова функція перевірки |
| FC-04 | Відкриття та повний життєвий цикл оплати | `check-51.sh`: справжній confirmPayment у тестовому Store з новою перевіркою; не iOS Store |
| FC-05 | XLSX/PDF підготовка категорій, маскування, account-filter | `check-export-report.sh`: pure builder; не рендер PDF на iOS |
| FC-06 | Видимий блок комісій та застосування Store-guard | статична перевірка змінених місць; UI і компіляцію Xcode ще потрібно перевірити |

## Наступні підетапи
1. Фінансова цілісність II: перевірити обмеження на загальний обсяг/суму фінансових записів, інваріанти кредиту та відновлення, кеші/періоди, повний графік розстрочок. Не підміняти прогноз фактичною історією.
2. UI-аудит: інвентаризація кожного доступного елемента і сценарію з результатом; захист незбережених чернеток; відтворення OCR/вхідної операції Build 69 у Xcode.
3. Надійність, міграції, продуктивність, release gate. Не видавати Linux за iPhone; стабільний IPA лише після повного Simulator і фінальної перевірки реального пристрою.
