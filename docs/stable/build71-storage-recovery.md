# Finami 6.4.23 / Build 71 — Storage & Recovery

База: Build 70 (6.4.22). Адаптовано концепції файлового сховища і політики снапшотів із наданого користувачем варіанта Build 57. Не відкотили фінансову логіку, дизайн чи OCR на Build 57.

## Збереження скриншотів

- `Database.scanFileHashes` — необов'язковий словник `scanImageID → SHA-256 JPEG`. Стара `scanImages` лишається підтриманою. Назва основної бази `Finora.json`, App Group, bundle ID та `IzanamiSnapshots` без змін.
- `FinamiScans/<sha256>.jpg`: атомарні, незмінні файли, захищені File Protection Until First User Authentication. SHA-256 від байтів збереженого JPEG (не від оригінального вхідного знімка). Однакові байти зберігаються один раз. Пошкоджений blob не перезаписується.
- Міграція при завантаженні виконується на існуючому фоновому шляху завантаження. Збережені та перевірені JPEG виносяться з JSON лише після створення перевіреної передміграційної копії і атомарного запису нової бази. Невдалі або конфліктні записи залишаються inline, без втрати байтів. `appearanceRevision` збережена.
- Нові збережені прев'ю до 1200 px. Роздільна здатність зображення для Vision OCR не змінена. Старі фото не перекодовуються.
- Квота нових фізичних файлів 64 МіБ; існуючі однакові файли можна повторно використати навіть на межі. Квота не поширюється на старі inline-вкладення, які не вдалося перенести. При перевищенні ліміту імпорт із новим вкладенням не записується; можна відмовитися від нового фото. Автоматичного видалення JPEG наразі немає. Це свідоме консервативне рішення: зберігаємо всі blobs, зокрема для старих снапшотів, undo, карантину і незавершених імпортів. Наступний підетап — безпечне прибирання тільки після перевірки всіх джерел посилань.
- Повний звичайний JSON і зашифрована копія знову вбудовують всі відомі вкладення (`scanFileHashes` у переносимій копії відсутній). Відсутність/пошкодження manifest blob або конфлікт inline/manifest блокує неповний експорт. Порожній `Data()` не видається за копію. Старі копії із вже відсутніми вкладеннями не можуть відновити їх автоматично.
- Локальне відновлення перевіряє hashes перед заміною даних. Зовнішній імпорт не приймає локальний manifest без повного переносимого JSON. Відновлення старого JSON з фото переносить їх за можливості, інші залишає inline.
- **Не встановлювати Build ≤70 поверх мігрованої бази без експорту повної JSON-копії.** Старі версії не знають про `scanFileHashes`. Не копіювати тільки `Finora.json` вручну як повну резервну копію. Перед першим встановленням Build 71 зробити звичайну або зашифровану копію з попередньої версії.

## Локальні копії та пошкоджена база

- П'ятихвилинний інтервал для звичайних змін. Без обмеження частоти для масового редагування, імпорту виписки, OCR-імпорту, legacy-імпорту, видалення операцій/рахунків/договорів та відновлення. Кількісні пороги політики не розпізнають кожну можливу фінансову/службову зміну; детальний ChangeSet — наступний етап.
- До 12 останніх + по одній копії за 14 календарних днів + по одній за 4 календарні тижні + до 8 останніх захищених точок. Групи можуть перетинатися. Копії без дати не видаляються автоматично; невдале видалення може залишити більше файлів.
- Наявні байти основного файлу використовуються без повторного кодування, якщо немає appearance-sidecar. Якщо є sidecar, snapshot кодує поточну базу в пам'яті. Структурна декодованість та записані байти перевіряються. Вкладення перевіряються при експорті/відновленні, не перечитуються при кожному снапшоті.
- Prune лише після успішної заміни основної бази. Якщо база не читається, звичайний запис заборонений. Перед явним відновленням пошкоджені основний файл і sidecar (якщо існують) копіюються byte-for-byte у `IzanamiSnapshots/Corrupt/<uuid>/`. Карантин не видаляється автоматично.
- AES-GCM і PBKDF2-HMAC-SHA256 600 000 без змін. Додано повідомлення про завелику копію та ранню перевірку верхньої межі розміру. Існуючий ліміт 150 000 000 байтів зашифрованого JSON збережено. Квота JPEG не гарантує, що дуже велика фінансова база або інші вкладення помістяться у цей формат.

## CI та якість

- `Build Finami IPA` делегує тому самому workflow `Test Finami on iOS Simulator` через `workflow_call`. Однаковий macOS-26 runner, повні регресії та UI-тести перед unsigned IPA. Push/PR проходять тести, не публікують IPA без явного параметра. Перевіряється відповідність версій застосунку й віджета і в release-пакуванні.
- Повернено попередження Swift про вирази >300 мс і функції >1000 мс. Масовий SwiftFormat і перейменування файлів відкладені до Code Quality.
- `Tests/check-storage-recovery.sh` компілює нові файлові механізми, фактичні методи `Store.write/commit/backupData/scanImageData/snapshotURLs` із мінімальними тестовими залежностями та перевіряє сценарії міграції, пошкодження, лімітів, відновлення і CI wiring. `check-load-database.sh` компілює фактичний метод завантаження. На Linux використовуємо тестову підстановку digest тільки в тестовому таргеті, бо CryptoKit недоступний. macOS використовує реальний SHA-256 та окремий тест відомого вектора. Повна компіляція iOS, фактична File Protection, криптографія на Apple SDK, XCUITest і CI reusable workflow залишаються до перевірки в GitHub Actions.

## Що не включено

Не змінювали фінансові формули, історію платежів, зовнішній вигляд, OCR-парсер і правила розпізнавання. Не переносили всі записи Store на фоновий потік, не робили повний ChangeSet, не запускали Instruments. Великі JSON та шифрування все ще можуть займати час на головному потоці. Автоматичне видалення файлів та ручний менеджер очищення відкладені, щоб спочатку перевірити відновлення. Це проміжна збірка стабілізації, не підтверджений iOS-реліз.
