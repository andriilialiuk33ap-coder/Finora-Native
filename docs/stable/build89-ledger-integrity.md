# Build 89 — Ledger Integrity (6.4.41)

База: Build 88. P0, перший етап. Дизайн, модель JSON, bundle ID, App Group та шляхи даних незмінні.

## Виявлено та виправлено

- `finamiValidGroupedBankParts` до цього перевірявся при restore, але не в загальному валідаторі. Тепер усі звичайні фінансові зміни, масові зміни, імпорт, завантаження та restore використовують цю перевірку. USD → UAH: явна сума в USD, валідний курс, UAH сума переказу = сума зарахування = сума всіх банківських частин; не допускаються порожні/повторні ключі всередині групи або одночасний окремий destinationBankKey. Глобальні повтори ключів між різними операціями залишаються предметом аудиту (Build 90), їх не видаляємо автоматично.
- Перевірка існування рахунків, заборона переказу на себе, UAH/USD, повна пара полів звірки, явна native amount і валідний курс для USD-джерела та явна destinationMinor для USD-призначення. База з USD-рахунками потребує чинного поточного курсу, як і раніше при restore.
- `LedgerIndex` використовує один рух для поточного й історичного балансу. Час кожної банківської частини збережено. Контрольний баланс включає рухи точно на дату звірки; для поточного залишку додаються тільки пізніші рухи. При інвалідації враховано також зміну reconciliationNet.
- Зв’язки refund/reimbursement перевіряються після перевірки меж сум, до публікації бази. Повернення лише на той самий рахунок; компенсація тільки між фактичними UAH-рахунками; разом вони не перевищують оригінальну покупку в нативних одиницях. Категорії синхронізуються при завантаженні, зміні й restore, без створення нових рухів.
- Кредитна корекція застосовує лише зміни показаного рахунку та підтвердженої ревізії; після зміни бази користувач повторно переглядає пропозиції. Відображає нативні суми та маскує приховані.

## Сумісність і межі

Не змінено жодного persisted-поля, міграція формату не потрібна. JSON зі суперечливим груповим переказом, відсутнім рахунком, неповною звіркою чи пошкодженим зв’язком не публікується; оригінал залишається на диску. Це навмисно суворіше, ніж у Build 88: якщо раніше некоректний запис відкривався, тепер знадобиться перевірена копія або окреме ручне виправлення з підтвердженням. Не виправляти суму групи або видаляти операції навмання.
